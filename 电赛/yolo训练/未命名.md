# 用大白话完整拆解这句话（专门适配你的 RDK X5 + YOLOv8 工程）

地平线 RDK 的 NPU（BPU）**不能直接跑 ONNX**，必须经过两步：

`ONNX浮点模型 → 量化校准 → 编译生成 .bin 模型`

> 量化：把 32 位浮点 FP32 模型转为 INT8，才能在 BPU 硬件加速，速度快、功耗低；
> 
> INT8 量化**不能凭空转**，需要一批真实图片作为【校准数据集】，告诉工具怎么压缩数值范围，防止识别精度暴跌。

你提到的 `mapper.py` 就是封装好的**一键自动化转换脚本**，代替你手动写配置、手动生成校准数据。

## 逐句翻译解释

### 1. 你需要提前准备两样东西

1. **你的 `best.onnx`（刚刚导出好的模型）**
2. **校准图片文件夹**
    
    ⚠️重点要求：
    
    图片必须和你板子**真实输入画面风格完全一致**！
    
    也就是：`640×360原图 → 上下填充黑边变成640×384` 的图片，
    
    不能随便拿网上照片，否则量化后精度严重下降、大量漏检。
    
    数量建议：**30～80 张**足够，不用几百张。

### 2. 脚本自动做的整套事情（不用你手动操作）

1. **自动生成校准数据**
    
    读取你给的校准图片，按照 YOLO 预处理流程（缩放、归一化、通道变换）预处理，生成校准用二进制文件；
2. **自动生成 yaml 配置文件**
    
    yaml 是模型编译配置：输入尺寸、均值 / 标准差、NPU 参数、输入输出节点、量化方式。
    
    不用你从零手写复杂 yaml；
3. **调用地平线工具链（hb_mapper）完成量化 + 编译**

### 3. 输出位置

转换成功后，最终能在 RDK X5 上 NPU 运行的 **`.bin` 模型**

直接输出到 **onnx 文件同一个文件夹里面**。

# 🎯结合你的项目给出实操规范（避坑重点）

## ① 校准图片硬性规范（最容易翻车！）

你的 ONNX 输入：`1,3,384,640` RGB

校准图片预处理流程 **必须和 RDK 上线推理 1:1 一致**：

ISP 640×360 → 上下填充 12px 黑边 → 640×384

> ❌大忌：只用 640×360 不带黑边的图做校准，量化后模型彻底失效

## ② mapper.py 运行前修改两处关键配置

打开 `mapper.py`，找到参数区域修改：

1. `onnx_model` = 你的 `/xxx/best.onnx` 路径
2. `calib_img_dir` = 存放校准图片的文件夹路径
3. 确认输入尺寸 `height=384，width=640`

## ③ 运行环境要求

必须在 **OpenExplore 地平线工具链环境**（Linux 虚拟机 / WSL / 容器）运行

Windows 原生 cmd 无法执行 hb_mapper 工具！

## ④ 完整流程顺序回顾

1. PC 训练 → 导出固定尺寸 `640×384 onnx` ✅（你已经完成）
2. 挑选真实场景图片，预处理成 640×384 作为校准集
3. 放入 OpenExplore 环境，配置 mapper.py 路径
4. `python3 mapper.py` 一键执行
5. 同级目录得到 `.bin` 模型
6. 将 `.bin` 传到 RDK X5 板子，写推理代码调用 BPU 运行

## ⑤ 额外概念区分

- `.onnx`：通用浮点模型（PC/GPU 运行，RDK BPU 不直接支持）
- `.bin`：地平线 BPU 专用量化模型（RDK X5 NPU 硬件加速唯一格式）

## ⑥ 常见失败场景提醒

1. 校准图片预处理方式 和 板子推理不一致 → 精度崩盘
2. 图片数量太少（<20 张）→ 量化漂移，识别效果变差
3. 图片分辨率不等于模型输入 640×384 → 直接转换报错
